## Принцип
Объём проверки пропорционален реальным рискам и затронутым зависимостям. Не сохранять тест ради количества, не считать зелёный статус доказательством непроверенного функционала. Не повторять одинаковые проверки одного SHA без причины. Не создавать новые отчёты/этапы только ради подтверждения предыдущих.

Отдельные коллекции, музыка, галерея, playback, загрузки, редакторы, навигация и т.д.; объединять выбранные наборы без дублей. Не запускать коллекции при правке отдельного загрузчика/плеера, если реальная зависимость отсутствует.
- Критические операции: storage/privacy/deletion/recovery/DB/shared architecture — соответствующие защитные тесты и lint; широкий verify при существенном/неизвестном риске.

Не нужно отдельное обоснование для каждого очевидного теста: кратко по группам. Не менять тест ради маскировки реального дефекта.

## 2. Раздельные QA и stable
Реализовать новый маршрут QA в том же ml-ci.yml, предложенное имя qa. Один запуск на конкретный SHA объединяет необходимые проверки по риску и ARM64/DEX. По умолчанию QA не требует full JVM/lint, если они не нужны по риску; выбранные проверки обязательны. Результат маркируется QA_ONLY / DEVICE_QA_PENDING, включает фактически выполненные и не выполненные проверки. Новый отдельный QA receipt должен быть явно поддержан gate/signing; не подделывать full qualification receipt и не обходить действующий gate. Обязательные условия любой доставки: успешная сборка, обязательные проверки выбранного профиля, DEX/целостность, точные исходники, оригинальный ключ и проверка сертификата. Подпись офлайн, доставка Drive, без эмулятора/main/merge/GitHub Releases по прежнему порядку.
Stable: полный актуальный JVM, lint, ARM64, DEX, exact-source qualification, затем устройство. Full также при существенных системных изменениях или накопленном риске, а не механически на каждый QA APK. Не объявлять QA стабильной без аппаратной приёмки и решения владельца. Если QA route ещё не внедрён, использовать прежний qualify, не обходить допуск.
