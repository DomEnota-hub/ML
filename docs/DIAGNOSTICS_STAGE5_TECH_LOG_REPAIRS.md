# MediaLoader — расширенная диагностика, этап 5/8: исправление журнала

**Основа:** PR #40 (этап 4, CI SUCCESS), приложение 1.7.6 (68).
**Ветка:** `feature/1.7.7-diagnostics-stage5-journal-polish`.
**Исходная задача:** Issue #37, выявлено при HTTP 403 резервного музыкального источника с VPN-сервером в Нидерландах.

## 1. Регистрация итогового сбоя поиска

В прежней реализации WebView писал `[DEBUG] [MuzmoWebView] HTTP error · mainFrame=true · status=403`,
но UI немедленно показывал «Музыкальный источник временно недоступен».
Оттого фильтр «Ошибки» оставался пуст: исходное событие было DEBUG.

В `MuzmoSearchDialog` теперь существует **второе, самостоятельное событие**:
- HTTP >=400 в основном документе *активного поиска* → `[ERROR] [Muzmo] Search document HTTP failure`;
- HTTP >=400 в основном документе выбранной композиции → `[ERROR] [Muzmo] Info page HTTP failure`;
- ошибка основного документа вне активной операции → `[WARN]`, не выдавать её за сбой подтверждённого действия;
- вспомогательный HTTP >=400 (скрипт, стиль, миниатюра) → только прежний `[DEBUG] [MuzmoWebView]`;
- 2xx/3xx не является HTTP-ошибкой;
- сбой подключения основного документа в активном поиске/выборе → отдельный `[ERROR]` по исходу операции; вне активного действия — `[WARN]`.

Это **ошибка выполнения конкретного действия**, а НЕ диагноз «MediaLoader сломан».
HTTP 403 сам по себе не доказывает причину (VPN/IP/доступ/защита ресурса).
Не переписывать старые DEBUG-события задним числом.

Существующая логика управления поиском/загрузками и сообщения пользователю
не изменены. Технический `AppLog`, его уровни и полный Markdown-экспорт
остаются нетронутыми.

Чистая функция `MusicHttpFailurePolicy` позволяет проверять классификацию
в JUnit независимо от Android WebView.

## 2. Русские пояснения и цветовые фильтры

`LogExplanation` распознаёт именно новые стабильные названия событий,
не копируя `op`, адреса сайтов, запросы или чувствительную информацию.
Для 403 явно сказано, что причина может зависеть от текущего VPN/IP,
а вина приложения не установлена. Для 429 рекомендовано не повторять
запросы слишком часто. Для других HTTP-кодов пояснение общее,
без выдуманного диагноза.

`LogDisplay` по-прежнему окрашивает строки согласно
**настоящему уровню сохранённого события**. В частности,
старый DEBUG HTTP 403 не превращается в ERROR, а новое терминальное
ERROR отображается и считается фильтром «Ошибки».

Примеры из наблюдения:
- `[DEBUG] [MuzmoWebView] HTTP error · mainFrame=true · status=403` — DEBUG;
- `[ERROR] [Muzmo] Search document HTTP failure · status=403` — ERROR;
- `[DEBUG] [MuzmoWebView] HTTP error · mainFrame=false · status=403` — DEBUG.

## 3. Управление журналом

Окно `Настройки → Журнал приложения` больше не использует
ограниченный по высоте `AlertDialog.text` с вложенным фиксированным
списком, который обрезал нижние действия.

Новый `Dialog`:
- ограничен размерами дисплея;
- основной список `LazyColumn` занимает свободную высоту и прокручивается;
- снизу постоянно доступны **«Обновить», «Очистить», «Закрыть», «Сохранить .md»**;
- переключатель «Пояснения в экспорт» остаётся отдельным и видимым;
- очистка открывает диалог с предупреждением и кнопками «Отмена»/«Очистить»;
- пока нет подтверждения, в `AppLog.clear()` не обращается;
- удаляются только технические журналы/архивы, а не файлы и история загрузок.

## 4. Проверки и ограничения

Новые JVM-тесты:
- `mainFrame=true` + активный поиск + HTTP 403 → ошибка операции;
- основной документ при открытии композиции → отдельная ошибка;
- `mainFrame=false` + HTTP 403/404/429/503 → отладочное событие;
- успешный 200 и перенаправление 302 не квалифицируются как HTTP-сбой;
- успешный повторный поиск не наследует статус прежнего HTTP 403;
- новый терминальный `[ERROR]` входит в фильтр «Ошибки»;
- старый `[DEBUG]` остаётся исходным DEBUG;
- пользовательское русское пояснение не раскрывает операционные идентификаторы.

CI: `testDebugUnitTest`, `lintDebug`, ARM64 `assembleRelease`, проверка ABI
и версии, существующие HitMoz/Muzmo JS-тесты.

**Оставшиеся ограничения:** реальный Android-диалог, маленькие дисплеи и
эффективность очистки при ошибке файловой системы нужно испытать на телефоне
после создания интегрированной тестовой версии. Старый фактический
пользовательский журнал в эту ветку не импортировался; тесты опираются
на анонимизированные характерные строки из скриншотов и исходный формат AppLog.

После CI отчитаться и остановиться перед этапом 6 до подтверждения пользователя.
