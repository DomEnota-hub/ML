# MediaLoader — расширенная диагностика: этап 3/8, источники

**База:** принятый этап 2 (PR #38), исходная версия MediaLoader 1.7.6 (68).
**Ветка:** `feature/1.7.7-diagnostics-stage3-source-checks`.

## Поддерживаемые источники

- Instagram
- YouTube
- VK
- RUTUBE
- Основной музыкальный источник (`hitmoz` — только внутренний код)
- Резервный музыкальный источник (`muzmo` — только внутренний код)

Название веб-сайта музыкального источника не появляется в тексте пользовательского
результата. Технические идентификаторы остаются в исходном коде.

## Три независимых измерения

### 1. Сохранённая сессия (локально, основные четыре источника)

`source.<id>.auth`: использует существующие readonly-признаки
`MediaRepository.isLoggedIn()`, `hasYouTubeCookies`, `hasVkCookies` и
`hasRutubeSession`. В отчёт не передаются ни токены, ни cookie.
Наличие сохранённых данных **не подтверждает** действительность входа на сервере;
отсутствие данных **не является** ошибкой для публичных материалов.
Результат — `UNAVAILABLE` с точным пояснением.

### 2. История загрузок (локально, все шесть)

`source.<id>.history`: считывает существующую `repository.downloads`
без редактирования записей и подсчитывает COMPLETED/FAILED/CANCELLED.
История ограничена доступными обычными строками; скрытые/очищенные записи
не восстанавливаются. Результат `UNAVAILABLE / HISTORICAL` либо
`UNAVAILABLE / NONE`, но никогда OK/ERROR по истории.

### 3. Анонимная сетевая доступность (шесть, только после отдельного согласия)

`source.<id>.http`: одно обращение к корню известного сайта.
Для обычных источников URL совпадают с начальной страницей в
`SourceBrowserScreen`; для музыкальных используются корни уже известных
`HitMozSearchClient` и `MuzmoDownloadUrls`:

- `https://www.instagram.com/`
- `https://m.youtube.com/`
- `https://m.vk.com/`
- `https://rutube.ru/`
- `https://ru.hitmoz.org/`
- `https://rmr.muzmo.cc/`

**Выполнение:**
- не запускается в локальном режиме;
- `WITH_NETWORK` в координаторе требует `networkConsent=true`;
- не делает поиск с пользовательским запросом, не отправляет cookies,
  не скачивает фото/видео/MP3 и не выполняет вход;
- `GET` только ради HTTP-статуса, **тело ответа не читается**;
- запрещён автоматический переход по HTTP 3xx;
- на запрос 5 с таймаута соединения + 5 с чтения, внешний лимит 12 с;
- не изменяет cookies, настройки, VPN, очередь, хранилище и журнал;
- не создаёт повторных запросов ради подтверждения успеха.

**Интерпретация:**
- 2xx означает только наличие HTTP-ответа для анонимного документа;
  исправность парсера, поиск, авторизация и возможность скачивания
  НЕ подтверждены;
- 3xx означает непроверенное перенаправление;
- 401/403 — ограничение анонимного доступа;
- 429 — сервер ограничивает частоту запросов;
- 5xx — удалённый сервер вернул ошибку;
- DNS/TLS/timeout/другая транспортная ошибка = `UNAVAILABLE`, причина
  на стороне приложения не предполагается;
- 403 может быть обусловлен IP/VPN, сессией или защитой ресурса;
  **автоматическое утверждение о неисправности загрузчика запрещено**.

Все пробы `DiagnosticImpact.OPTIONAL`. Они не создают глобальный красный
статус приложения при отказе отдельного сайта.

## Реализация

- Чистая Kotlin-политика: `core/diagnostics/SourceDiagnosticRules.kt`.
- Android-адаптеры, инъекция транспорта для тестирования:
  `data/diagnostics/SourceDiagnosticProbes.kt`.
- Объединённый реестр для всех этапов:
  `data/diagnostics/MediaDiagnosticRegistry.kt`. Только создание объектов,
  **никаких запросов при конструировании**.
- Из локальной фабрики этапа 2 выделено `LocalDiagnosticProbes.probes`,
  прежний `LocalDiagnosticProbes.create` сохранён.
- Unit tests для шести источников, сохранённых cookies, истории,
  HTTP 2xx/3xx/401/403/429/5xx, транспортных ошибок и оценки общего статуса.

## Ограничения и последующие работы

**На этапе 3 не реализуются:** проверка действительности серверной
авторизации, контроль реальных загрузок, диагностика парсеров на живых
страницах, OAuth-пробы, WebView-авторизация, тестовые скачивания,
диагностический экран и автоматическое фоновое сканирование.

Показатели успешности анализаторов в будущей диагностике должны опираться
на структурированные события с привязкой к операции, а не на ненадёжный
поиск по произвольным текстовым DEBUG-строкам. Это часть будущего журнала
неисправностей и отдельного этапа Issue #37.

При CI: unit tests, lint, ARM64 assemble. После проверки дать отчёт и
**остановиться до пользовательского подтверждения этапа 4**.
