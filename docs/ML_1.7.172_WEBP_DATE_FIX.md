# ML 1.7.172 / code232 — WebP под расширением .jpg

## Подтверждённая причина

Предоставленный Instagram_50_1.jpg имеет MIME image/jpeg в Drive/старой записи, но заголовок RIFF/WEBP. Размер 53344 байта, 1440×1686, VP8X + ICCP + VP8. JPEG-проверка обоснованно отклоняла эти байты до изменения оригинала.

## Исправление

Кодек определяет WebP по содержимому проверенного резерва, независимо от .jpg. WebpHeaderDates сохраняет исходные сжатые блоки изображения, ICC-профиль и остальные непрозрачные блоки побайтно. Добавляется EXIF TIFF с датами DateTime/DateTimeOriginal/DateTimeDigitized и часовым поясом; в VP8X включается EXIF-флаг. Для обычных VP8/VP8L без расширенного заголовка он создаётся по исходным размерам/прозрачности без перекодирования.

Проверяются RIFF-размер, границы/число блоков, структура заголовка, даты, флаги/размеры и SHA-256 всех исходных блоков вне разрешённой метаинформации. В Android дополнительно требуется прочитать EXIF-дату платформенным ExifInterface и совпадение декодированных пикселей через существующую ограниченную по памяти проверку. Анимация, существующий EXIF, неизвестные/повреждённые заголовки отклоняются до изменения оригинала; JPEG/MP4-проверки не ослабляются.

В журнал v1 добавлено необязательное contentMime. Оно определяется по хеш-проверенному резерву до публичных изменений. Разрешено только прежнее значение или подтверждённый переход image/jpeg→image/webp. Идентичность MediaStore допускает исходный MIME и подтверждённый фактический MIME, если сканер уточнит тип. Имя .jpg, URI-перепривязка, downloadId, история и остальные связи сохраняются. Никакого преобразования WebP в JPEG нет.

## Адресные проверки

- Четыре JUnit-теста нового модуля PASS, Kotlin 2.0.21 напрямую: расширенный WebP с ICC, обычные VP8/VP8L с альфа-каналом, повреждение ICC, обрезанные/неверные RIFF, анимация/существующий EXIF. Исходные искусственные файлы неизменны.
- Выполнен код WebpHeaderDates приложения на пользовательском файле и двух искусственных WebP. Pillow/libwebp подтвердили точное равенство декодированных пикселей, размеров и ICC, EXIF-дату и UTC-смещение; встроенная проверка подтвердила идентичность сжатых блоков. SHA-256 исходников остались прежними. Фото и его производные в git не добавляются.
- Порядок чтения WebP EXIF сверён с реализацией android.media.ExifInterface Android 14: EXIF-блок передаётся непосредственно TIFF-парсеру. Подтверждение на прошивке телефона остаётся необходимым; приложение само проверяет чтение EXIF перед заменой.
- Полный suite/debug/lint/emulator/проверки сторонних модулей не запускаются. MP4-исправление 1.7.171 сохранено, широкие повторные прогоны не требуются.

## Продолжение

Установить поверх текущего приложения без очистки данных → «Продолжить по журналу». На BACKUP_VERIFIED ещё нет подтверждённого результата newHash: копия текущего Instagram_50_1.jpg будет подготовлена заново по фактическому формату. Уже завершённые замены и оставшаяся очередь сохраняются. Резерв оригинала остаётся; неподдерживаемые случаи продолжают останавливаться безопасно.
