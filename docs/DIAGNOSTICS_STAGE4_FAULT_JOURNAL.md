# MediaLoader — расширенная диагностика, этап 4/8: журнал неисправностей

Основа: PR #39 (этап 3, CI SUCCESS), исходная версия приложения 1.7.6 (68).
Рабочая ветка: `feature/1.7.7-diagnostics-stage4-fault-journal`.

## Реализовано

- **Отдельная структурированная история неисправностей** (`FaultJournal`, `FaultSignal`,
  `FaultRecord`), независимая от технического `AppLog` и его Markdown-экспорта.
- Сведения об инциденте: внутренний непрозрачный ID; компонент; точный код проверки;
  подтверждённый код причины; необязательный непрозрачный ID операции; уровень
  WARNING/ERROR; состояния ACTIVE / NEEDS_RECHECK / RESOLVED; время первого
  и последнего появления, время устранения, число повторов, ссылки на события.
- Консервативная группировка: только однотипные повторные неисправности
  **того же компонента, кода проверки, причины и идентификатора операции**.
  Ошибки другого источника, задачи или операции не смешиваются.
- Неактуальные / уже учтённые повторно сигналы не увеличивают счётчики.
  После подтверждённого устранения следующее возникновение открывает
  самостоятельный инцидент. Исторические устранённые инциденты сохраняются.
- Автоматическое устранение возможно только после **подтверждённого успешного
  результата той же конкретной проверки**, а не другого компонента.
  Неисполненные (UNCHECKED), исторические (HISTORICAL) и ошибочные
  диагностические проверки (UNAVAILABLE) не закрывают неисправности.
  Повторный запуск с недоступным результатом переводит существующий
  инцидент в NEEDS_RECHECK, не объявляя его устранённым.
- `FaultExplanations`: словарь статических русских объяснений и рекомендаций
  для известных проверок (HTTP 403 / 429 / 401 / 5xx, ошибки папки, модели
  LaMa, runtime). Не извлекает текст из URL, cookie, имен файлов,
  exception.message или произвольных raw-логов.
- Локальное `FaultJournalStore`: `filesDir/diagnostics/fault-journal-v1.json`,
  отдельная атомарная запись, ограничение 300 записей, 16 ссылок на инцидент,
  лимит JSON 1 МиБ, проверка версии формата и содержимого. При повреждении
  данных запись запрещается до явного разрешения проблемы — журнал не
  перезаписывается пустым.
- `DiagnosticJournalRunner` связывает **завершённый** `DiagnosticRun` с
  журналом. Не вызывает диагностику сам, не планирует проверок по расписанию.
  Отменённые запуски не сохраняются как завершённые.
- Операционные события можно передавать явно через
  `FaultHistoryStore.record(FaultObservation)`; идентификатор операции
  передаётся как отдельное поле и не должен включать адреса/секреты.
- `FaultJournalCodec` — отдельный версионированный JSON-кодек;
  JVM-тесты на сохранение и повреждённые/слишком большие записи.

## Границы этапа

**Не изменялось:** исходный AppLog, классификация его DEBUG/WARN/ERROR, журнал
в настройках, логика работы резервного музыкального источника, загрузки,
авторизация, пользовательский UI, полные `.md`-экспорты.

**Ещё не реализовано:**
- Экран журнала неисправностей, фильтры, подтверждение очистки.
- Привязка диагностического runner к UI и реально выполняемым проверкам.
- Восстановление связанных событий в UI: исходный AppLog не выдаёт
  глобально уникальные идентификаторы каждой строки; точные ссылки доступны
  лишь если будущая телеметрия предоставит непрозрачный event ID.
  До этого не показывать неработающие кнопки перехода к событию.
- Автоматическое выявление пользовательского сетевого сбоя по исходной DEBUG
  строке MuzmoWebView: **предмет отдельного этапа Issue #37**. Не превращать
  любой HTTP 403 в ERROR без финального результата операции.

## Тестирование

- Раздельная группировка по checkCode, reasonCode, component, operationId.
- Успешная проверка одного кода не закрывает ошибки других проверок.
- Невыполненная/недоступная проверка не закрывает инциденты.
- Сохранение исторических устранённых случаев.
- Ограничения повторов/ссылок и отклонение приватных идентификаторов.
- JSON roundtrip, ошибки версии/структуры, запрет пустой подмены при
  повреждении, ограничения размера.
- Отмена/отсутствие сетевого согласия не пишут журнал.
- CI Kotlin/JUnit, Android lint и контрольная ARM64-сборка.

После успешного CI пользователь получает отчёт, а перед следующим
этапом работу необходимо остановить до подтверждения.
