# MediaLoader 1.7.224 · Этап 2: состояния поиска и фильтры дубликатов

Дата: 23 ноября 2026 года, МСК. Ветка `feature/ml-17224-inapp-folder-picker`, Draft PR #189. База — подписанная QA 1.7.223, исходный SHA `23291b25177a02c7f136781afa677946e846dd73`.

## Исходный дефект

На Xiaomi Android 16, 23.11.2026 20:43, пользователь видел «Все», «Точные · 0», «Акустика · 0», «Версии · 0» на экране Музыки **до запуска поиска**. Это бесполезные элементы и визуально занимает место. Состояние до поиска и состояние без найденных совпадений не должны выглядеть как результаты с нулевыми категориями.

## Внесено в исходники (проверено чтением точного кода)

1. Введён `DuplicateResultFilterPolicy`: счётчики из фактически существующих групп, список только категорий с ненулевыми значениями, возврат устаревшего выбранного типа к «Все» без изменений сохранённого отчёта.
2. Общий `MusicDuplicateResultFilters` используется для подтверждённых и предварительных групп. При нуле групп вообще не создаёт строку фильтров; при находках показывает «Все» и только реально существующие категории. Размещение адаптивное, по две категории в строке.
3. В `MusicDuplicatesDialog` до поиска показываются выбор режима/запуск и явное пустое состояние; фильтры появляются только при наличии найденных групп. При живом поиске предварительные категории основаны на `partial.groups`; фильтрация предварительных результатов не разрешает удаление. Отдельно сохранены текущие операции паузы/отмены/восстановления.
4. В `VisualDuplicatesScreen` категориями Галереи управляет `VisualDuplicateResultFilters`: только фактически найденные типы, а при нулевом результате — «Совпадений не найдено». Смена типа не должна оставлять список на прежней прокрученной позиции.
5. Устаревший выбранный фильтр автоматически трактуется как «Все» после исчезновения соответствующих групп при обновлении результата.

## Регрессионные тесты, добавлены в обязательный реестр

Добавлены 11 новых ID: пять `DuplicateResultFilterPolicyTest`, три `MusicDuplicateResultFiltersTest`, три `VisualDuplicateResultFiltersTest`. Обязательный JVM inventory вырос **2463 → 2474**, ранее разрешённый Shazam skip сохранился, старые ID не удалялись.

Проверяемые сценарии: (а) до поиска нет ни одной категории; (б) одна категория с ненулевым счётчиком не вызывает остальные нулевые категории; (в) категории показываются в согласованном порядке; (г) прежний фильтр, который исчез в обновлённом результате, безопасно переводится на «Все»; (д) переключение категорий не инициирует поиск само по себе.

**Важно:** изменения и тесты сохранены, но Gradle/JVM/lint, полный CI и аппаратная QA **не выполнялись**. Роботизированные Compose-тесты на API 34 не подтверждают UI на реальном Xiaomi Android 16.

## Аппаратная приёмка

1. Открыть Музыку → Дубликаты при чистой истории без поиска. «Все / Точные / Акустика / Версии» отсутствуют; видны настройки режима и кнопка запуска.
2. Запустить поиск без находок. Пока нет групп — фильтров нет; виден прогресс и доступные действия. После окончания — сообщение об отсутствии совпадений, никаких четырёх пустых фильтров.
3. Найти только точные группы: доступны «Все» и «Точные», без «Акустика» и «Версии». При наличии нескольких видов отображаются только найденные категории и верные числа.
4. Проверить предварительные группы во время поиска, остановку/возобновление, восстановление сохранённого отчёта, смену поиска и изменение результата.
5. В Галерее проверить отсутствие пустых категорий, а также фильтры подтверждённых результатов при обновлении каталога.
6. Не терять выбранные файлы, результаты, приватность, журналы и правильное состояние кнопки из этапа 1.
