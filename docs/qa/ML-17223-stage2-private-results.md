# MediaLoader 1.7.223 · этап 2 · поиск дубликатов и перенос в «Личное»

Дата: 23.11.2026 (МСК). Ветка: `feature/ml-17223-qa222-device-regressions`, Draft PR #187.

## Дефект и проверенные причины

При переносе публичного файла в «Личное» `MediaRepository` передаёт `DuplicatePrivacyGuard.revoke` ID и заранее собранные публичные алиасы. Ранее `revoke` **всегда** повышал глобальную эпоху и удалял отчёты обеих медиатек, журналы, checkpoints и кеши, даже если переносимый файл ни в одной группе результатов не участвовал. Сохранение старых файлов отчёта без миграции/проверки эпохи **не является исправлением**: readers проверяют `privacyEpoch`.

## Исправление, реализованное в исходниках (пока не квалифицировано)

Добавлен `DuplicatePrivacyRetention`: перед отзывом доступа, под общим блокирующим монитором хранилищ, проверяет все известные публичные отчёты, JSON/JSONL shards, текущие результаты и partial в памяти, а также `AtomicFile` companions. Сопоставление выполняется по ID, нормализованным URI и алиасам MediaStore, а если есть физический `file-stat` — по реальным файловым идентичностям для ограниченного набора публичных URI. Числовые границы объёма обязательны для защиты от зависания; всё неизвестное, повреждённое или слишком большое приводит к старому строгому сбросу.

Только если **все** данные доказуемо не относятся к переносимому файлу и нет текущего сканирования, публичный ID и его алиасы блокируются сразу **без увеличения поколения отчётов**. Сохранённые результаты/журналы остаются открываемыми, старые выборы и checkpoint не теряются.

При любом совпадении, активном поиске, отсутствии идентификаторов, невозможности проверить inode/URI или ошибке чтения остаётся прежний полный `revoke`: увеличение эпохи, очистка отчётов, отмена сканирования. В обоих случаях вычисленные музыкальные/визуальные/распознавательные кеши очищаются; приватный файл ни при каких обстоятельствах не должен оставаться доступным.

Никаких данных приватных файлов в отчёт и репозиторий не добавляется.

## Статические проверки и тестовая база

Добавлено 5 методов `DuplicatePrivacyRetentionTest` на сохранение независимого отчёта, совпадение по чужому ID через URI, совпадение по истории, повреждение и AtomicFile recovery, непроверяемые физические алиасы. В существующем тесте `DuplicateScanScopeDialogTest` с первого этапа — ещё 2 метода. Все семь ID добавлены в обязательный `docs/ci/required-jvm-tests.json`; старые 2438 идентификаторов/ожидаемые статусы не удалялись и не менялись.

**Статус:** `SOURCE_COMMITTED / STATIC_REVIEW_ONLY / JVM_NOT_RUN / LINT_NOT_RUN / CI_NOT_STARTED / DEVICE_QA_PENDING / NOT_STABLE`. Парсинг исходников и diff не заменяют компиляцию, тест или измерение на Xiaomi. Строгое поведение при неоднозначности сохраняется.

## Для финальной QA на Xiaomi Android 16

1. После завершённого поиска Галереи перенести в «Личное» **посторонний** файл, не входящий в группы, проверить сохранение результата, истории, выбранной области и возможность открыть результат после перезапуска приложения.
2. Повторить с Музыкой и незавершённым checkpoint; проверить историю после фоновой паузы.
3. Перенести файл, **входящий** в группу результатов; убедиться, что доступ/миниатюра/прослушивание закрыты, старые данные не возвращаются при восстановлении и перезапуске.
4. Проверить разные ID одного публичного источника (MediaStore URI, app ID, файловые алиасы). При неподтверждённой идентичности — строгое состояние без раскрытия приватного файла.
5. Проверить быстрый перенос нескольких файлов, повторный просмотр, восстановление приватного файла, процессы Android и нажатия на корзину.
6. Записывать только необходимые диагностические метаданные, **не** загружать пользовательские медиа и сырые логи в GitHub.

Следующая разработка только отдельным логическим этапом. Полный `qualify` один раз на замороженном итоговом SHA согласно `docs/ci/README.md`, затем подпись DomEnota, доставка Google Drive и физическая QA. До этого 1.7.223 не называть стабильной.
